## 2. Підтверджена первинна причина (в коді бази)

- `djonikClient.ts` (база): **один** стан `unverifiedTrelloWrite/pendingWriteTool/pendingWriteObjectId/pendingWriteDue` — наступний запис перезатирав вимогу до попереднього (R2).
- `writeObjectId()` читав `input.cardId`; у create його немає → `pendingWriteObjectId === null` → гілка «будь-яке успішне читання Trello знімає вимогу» (R1).
- Жодна перевірка не дивилась на **результат** запису чи читання: верифікація була лише «вхід читання називає той самий id».
- `findDueField()` рекурсивно (глибина 3) шукав перший `due`-подібний рядок у будь-якому вкладеному об'єкті + regex-фолбек по сирому тексту (R6).

## 4. Точний дизайн стану верифікації

Створюється новий `TrelloMutationLedger` на кожен видимий turn (скидається в `sendPartsSerial`, живе через корективний nudge). Події:

- `recordToolUse` → монотонний `useSeq`; `recordToolResult` (за `mcp_tool_use_id`) → `resultSeq`, `isError`, `content`. Реєструються лише Trello read/write виклики.
- `outcomes()` — чиста функція над записаними подіями; повертає по одному `MutationOutcome` на кожен `trelloWrite*` виклик, у порядку викликів:

| status | значення | nudge допомагає? | блокує «успіх»? |
|---|---|---|---|
| `verified` | усі запитані поля підтверджено валідним читанням після запису | — | ні |
| `due_differs` | (**раунд 2**) читання валідне, решта полів збіглась, але Trello тримає **інший** парсований `due`, ніж запитано (#23) — термінальний, авторитетний | **ні** (перечитування нічого не змінить; повтор запису заборонений) | ні; відповідь — детермінований «Trello підтвердив дедлайн X… відрізняється» |
| `awaiting_read` | ціль відома, валідного прямого читання після запису ще нема | так | так |
| `field_mismatch` | читання валідне, але запитане поле має інше значення | так (перечитати) | так |
| `field_unconfirmed` | читання валідне, але значення поля відсутнє/нерозбірне | так | так |
| `target_unknown` | немає однозначної ідентичності картки (або не-card write tool) | **ні** | так |
| `no_result` | немає result-події виклику запису | ні | так |
| `failed` | `is_error` — **авторитетно незастосований**; несе обмежений текст помилки інструмента | **ніколи** (повтор може дублювати) | ні, але **відповідь моделі не використовується** — див. §10/§19 |

Кожен `MutationOutcome` містить `toolUseId`, `targetCardIds`, `label` (запитана назва, лише для звіту), `unconfirmedFields`, `superseded`, `due{intendedDue, verifiedDue}`.

## 5. Як встановлюється ідентичність створеної картки

- `action: "create"`: ціль = `id` з **власного успішного результату** цього запису. `input.cardId` у create **ніколи не довіряється**.
- Результат мусить бути одним об'єктом картки: розібраний JSON-текст із рядковим непорожнім `id`, або обгортка з єдиним ключем `{card:{…}}`. Нічого глибшого; масиви/пошукові відповіді не є карткою; два текстові блоки з різними id — неоднозначно.
- Немає такого id → `target_unknown`; жодне наступне читання цього не виправить (nudge не надсилається).
- update/move: ціль = `input.cardId`; якщо результат теж називає id і вони **явно конфліктують** — `target_unknown`. id порівнюються за останнім окремим 24-hex ObjectId (bare/ARI/регістр), інакше — рівність токенів.

## 6. Кілька одночасних/послідовних мутацій

- Кожен запис — окремий запис у журналі; пізніший запис не змінює вимог до раніших.
- Запис A + запис B + читання лише B → B `verified`, A `awaiting_read` (nudge просить перечитати лише A).
- Один запис за замовчуванням не «використовується» для іншого: читання картки A не підтверджує B.
- Той самий картка, кілька записів: **останній запис поля володіє полем**; раніший запис, чиє поле перезаписане, успадковує результат власника (`superseded: true`, у звітах не дублюється). Різні поля перевіряються окремо. Опорне читання — найпізніше валідне читання після запису; пізніше читання перекриває застаріле. Читання між двома записами підтверджує лише перший.
- Спроба «повторити запис» під час nudge — це **нова** відстежувана мутація; вона не «відмиває» оригінал.

## 7. Як прямі читання зіставляються з мутаціями

Читання підтверджує запис лише якщо одночасно: `trelloReadCard` з `action: "get"` (або без action); **успішний** (`is_error=false`); **його tool-use почався після result-події запису** (`useSeq > resultSeq` — читання, що стартувало до завершення запису, могло показати стан до запису); вхід називає картку (`cardIdOrUrl`/`cardId`); результат — один об'єкт картки, чий власний `id` збігається з ціллю запису; вхід і результат не суперечать один одному. Не рахуються: читання до запису, `trelloSearch`, board/list/member, `list_by_board`, читання іншої картки, помилка, неоднозначний/нерозбірний/без-id результат.

## 8. Як перевіряються постумови змінених полів

Поля з вхідних даних запису → перевіряються на об'єкті картки з опорного читання: `name` (`title`), `desc` (`description`) — порівняння з trim та нормалізацією CRLF; `list` (`listId`/`idList`) — `card.list.id` / `idList` / `listId`; `due`. Результат поля: збіг / розбіжність (→ `field_mismatch`) / відсутнє (→ `field_unconfirmed`). Запис без жодного відомого поля підтверджується лише читанням картки. Покриває create/update/move/due без розширення поверхні інструментів.

## 9. Виправлення витягу due

`extractVerifiedDueFromTrelloReadContent` = `extractCardObject(...)` → лише власне `due` цієї картки, що є валідним UTC ISO (`…Z`). Рекурсію та regex-фолбек по сирому тексту видалено. Критична фікстура `{id:"cardA", due:null, board:{due:"…"}}` → `null`. У ledger: запит `due` підтверджується лише парсованим `due` **об'єкта картки**; явний `null` → `field_mismatch`; відсутнє/нерозбірне → `field_unconfirmed`. Збережено #23: іншопарсоване due = статус `due_differs` (§19.2) з наявним формулюванням «відрізняється від відправленого»; Europe/Kyiv через `Intl`; для одного verified-запису due — точне #23-речення. Кілька verified-мутацій з due → по одному детермінованому рядку на мутацію (жодного слова моделі). Запит на очищення (`""`/`null`) підтверджується лише явним `null`; жодного обхідного шляху для очищення due не додано.

## 10. Поведінка при partial / failed / ambiguous

- Усе `verified` (без `failed`) → відповідь моделі без змін (крім #23-заміни для due).
- **Будь-який `failed` (tool-error) запис → відповідь моделі НЕ використовується взагалі** (раунд 2, §19). Користувач бачить лише детермінований звіт із подій: `❌ Не виконано (помилка інструмента): «…» (id) — <обмежений текст помилки інструмента>` плюс `✅`/`⚠️` рядки для підтверджених мутацій. Це стосується і єдиного failed-запису, і failed+verified.
- Хоч одна `unresolved` (`awaiting_read`/`field_mismatch`/`field_unconfirmed`/`target_unknown`/`no_result`) після одного nudge → `DjonikUnverifiedMutationError`. Message: старий рядок `Djonik mutated Trello but did not verify the write…` + детерміновані `✅`/`⚠️`/`❌` рядки по **кожній** мутації (включно з failed і due_differs). `modelReply` доступний лише як дані, не як результат.
- `due_differs` (§19.2): термінальний детермінований результат, не unresolved, без nudge.
- Ambiguous create, невідома форма результату, не-card write tool → `target_unknown`, без nudge (fail-closed, без автоматичного повтору).
- Nudge: не більше 1; називає лише **нерозв'язані** картки (не failed, не verified, не due_differs); містить «НЕ повторюй запис і не створюй нову картку».

## 19. Follow-up review (раунд 2) — точні виправлення

### 19.1 BLOCKING: failed-мутація більше не може дати model-authored хибний успіх

**Проблема раунду 1.** Статус `failed` не блокував успіх, а коли єдина мутація `failed`, відповідь моделі поверталась без змін → `trelloWriteCard → is_error=true → модель: «готово»` доходило до користувача.

**Виправлення (детерміноване, без парсингу прози / intent-роутера).** `is_error` результат — авторитетний failed-outcome. `finalizeMutationReply` (`src/djonikClient.ts`): якщо **хоч одна** мутація `failed`, то повертається лише `describeMutationOutcomes(outcomes, …)` — звіт зі статусів подій; текст моделі не читається й не повертається (ні для одного failed, ні для failed+verified). Для failed+unresolved так само — `DjonikUnverifiedMutationError`, чий message містить `❌` рядок для failed (текст моделі в message не входить). Ledger (`src/trelloMutationLedger.ts`): `failed`-outcome несе `errorText` (текст помилки інструмента, схлопнуті пробіли, ≤200 символів + «…») і display-only ціль (`cardId` для update/move; для create — без id, бо create не довіряє input `cardId`). Нових API/інструментів немає.

**Без дублювання/повтору.** `failed` не входить у `NUDGEABLE_STATUSES`, тож nudge не надсилається через нього; nudge при failed+unresolved називає лише нерозв'язану картку і містить «НЕ повторюй запис». Повтор запису моделлю під час nudge — **нова** відстежувана мутація; оригінальний failed-рядок лишається у звіті й не «відмивається».

### 19.2 Семантика due mismatch (#23) — явна й узгоджена

Раніше ledger називав розбіжний `due` «verified», а звіт — «mismatch»: назва статусу не відповідала постумові. Тепер:

| Що бачить прямe читання картки | Статус | Nudge | Результат |
|---|---|---|---|
| `due` = запитаний (той самий інстант, будь-який формат рядка) | `verified` | ні | точне #23-речення «Готово. Trello підтвердив дедлайн: …» |
| `due` — **інший парсований** UTC-інстант | **`due_differs`** (новий) | **ні**, не unresolved | «Картку оновлено, але Trello підтвердив дедлайн: <verified Kyiv>. Це відрізняється від значення, яке було відправлено.» — **лише verified due, запитане ніколи не подається як факт** |
| явний `due: null` після set-due | `field_mismatch` | так (1 раз: може бути застаріле читання) → fail-closed | throw |
| поле `due` відсутнє/нерозбірне/не-UTC | `field_unconfirmed` | так (1 раз) → fail-closed | throw |
| розбіжність іншого поля (name/desc/list) поруч з due | `field_mismatch` (переважає) | так → fail-closed | throw |

`due_differs` — термінальний: повторне читання не змінить авторитетне значення, тому **ні nudge, ні повтор запису**. Він враховується як «підтверджено читанням» (`isConfirmed`), не блокує успіх, але відповідь завжди детермінована. У багатомутаційних/партіальних звітах (`describeMutationOutcomes`) due-рядки будуються тим самим `describeDueForUser` (лише verified due; `⚠️` для розбіжності, `✅` для збігу). Trace `due_date_reply_finalized.mismatch` збережено.

### 19.3 Точна межа #31 / #32

**#31 (зроблено):** коректність мутацій — кожен запис прив'язаний до своєї цілі й результату; failed/unverified/ambiguous/differing-due ніколи не подаються як успіх; fail-closed; жодного повтору запису; детермінований звіт із подій.

**#32 (свідомо відкладено, НЕ реалізовано тут):** збереження **непов'язаного змішаного виводу**. У turn, де є `failed` або unresolved мутація, текст моделі не повертається (бо він може стверджувати успіх цієї мутації, а відділити це від непов'язаного змісту можна лише парсингом прози/intent-логікою). Наслідок: непов'язані частини відповіді моделі в такому turn не доходять до користувача; доходить чесний звіт про мутації. Так само лишаються за #32: кореляція пізніх/повторно використаних результатів specialist, R3–R5/R7, завершеність turn, збереження змішаної відповіді на рівні relay. У turn **без** failed/unresolved мутацій змішана відповідь модель зберігається як і раніше (крім #23-заміни для verified due-запису).

**Підтвердження:** #31 лишається fail-closed для коректності мутацій — жодна failed, unresolved, ambiguous чи розбіжна за due мутація не може бути описана як успішна текстом моделі.
