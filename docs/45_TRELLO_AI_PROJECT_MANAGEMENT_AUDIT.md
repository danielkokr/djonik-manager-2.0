## 1. Executive conclusion

1. **Trello — раціональний субстрат. Проблема не в Trello, а в тому, що картки не несуть сигналів, які Djonik мусить знати.** Єдиний hard failure останнього smoke ([docs/43](43_ISSUE_38_CONTRACT_DERIVED_LIVE_SMOKE.md) §10) — «без дедлайну — чекає без ризику». Модель вгадала ризик із відсутності due, бо зафіксованого зобов'язання в картці просто немає. Саме цю дірку має закривати інформаційна архітектура, а не черговий рядок у Skill. **MEDIUM**
2. **Скелет правильний:** одна дошка, проєкт = label, список = стадія життєвого циклу. Залишити. **STRONG** для нашого контексту: на цьому вже стоять #36 (scope за label), #37 (label при create) і Project Health.
3. **Запропонована тріада Priority / Size / Focus — надлишкова в такому вигляді.**
   - **Priority на кожній картці — прибрати як обов'язкове поле.** Для соло-дизайнера з п'ятьма клієнтами пріоритет переважно **проєктний**, і він уже є в Memory `work-priorities.md`. Картці потрібен лише **виняток**: «важливіше/менш важливе за проєкт». Поле, де 80 % карток мають «Medium», не несе інформації.
   - **Size — залишити, але спростити** до 4 кошиків із калібруванням у годинах і дозволити пряму оцінку («~2 год»). Години — це те, з чим реально рахує денний план.
   - **Focus — не робити полем.** Це м'яке судження з низькою ціною помилки. Модель може вивести його з назви й опису, якщо **назве це своєю думкою**. Додати опційний маркер, коли він неочевидний.
4. **Найцінніше поле, якого зараз немає, — `Зобов'язання`** (кому, що, до коли), окремо від Trello `due`. Друге — **`Наступний крок`** для In progress і **`Чекаю`** для Waiting. Ці три рядки дають найбільше покращення міркувань на одиницю зусиль Daniel. **MEDIUM**, узгоджується з GTD next action / waiting-for і з product contract «client commitments distinct from internal due dates».
5. **Custom Fields vs опис: зараз — лише опис.** Причини:
   - офіційний Trello MCP не віддає Custom Fields. Це підтверджено вашим probe і [публічним roadmap](https://github.com/atlassian/trello-mcp-server), де Custom Fields у «coming soon» **[EXT, STRONG]**;
   - Djonik також **не може записати** Custom Field. Тобто самостійне збагачення карток сьогодні можливе тільки через `desc`, а `desc`-записи вже точно верифікуються #31 **[REPO]**;
   - Trello Automation не вміє **замінювати** блок в описі: немає replace/regex, лише `{carddescription}` + дописування. Тому синхронізація «поле → опис» дублюватиме блоки **[EXT, STRONG за відсутністю функції в офіційних docs]**;
   - на дошці вже визначені поля `Priority` (6 значень) і `Size` (5), але значення має **1 картка з 41** [REPO, замір]. Міграційна ціна зараз нульова, і це найкращий момент перестати їх заповнювати.
6. **Формат метаданих:** 2–5 коротких рядків `Ключ: значення` **на початку опису**, фіксований словник ключів і значень. Без `[AI META]`-обгорток: вони потрібні лише коду-парсеру, а людині заважають. Рядок є лише тоді, коли є значення. Відсутній рядок означає «невідомо», а не «низько» чи «ні». **MEDIUM**
7. **Прогресивне збагачення**, прив'язане до переходу між списками, а не до створення. Inbox — лише назва (+ проєкт). Вимоги з'являються тільки при «This week / In progress / Waiting», і вони м'які: Djonik пропонує дозаповнити **пакетно в ритуалах** (понеділковий план), а не ниє щоходу.
8. **Djonik може записувати факти, які Daniel сам сказав** («займе десь 2 години»), але **лише після короткого підтвердження**, з одним «так» на кілька карток. Власні висновки моделі (розмір, фокус, ризик) у картку не пишуться: вони лишаються судженням у розмові. Це тримає межу «факт Daniel ≠ оцінка AI». **MEDIUM**, узгоджується з Linear AIG і нашим контрактом «autonomous turns never change Trello».
9. **Інфраструктура: нічого нового зараз.** Не ставити community MCP, не будувати automation bridge, не робити зовнішню БД. На **пізніше**: дочекатися Custom Fields в офіційному MCP і тоді вирішити, чи переносити заголовок опису в поля. Проміжний варіант — read-only custom tool на наявному REST-патерні #36. Він технічно дешевий, але лише якщо пілот покаже, що опису недостатньо.
10. **Найбільший важіль для токенів — не метадані, а Done-картки.** Це 20 із 41 відкритої картки. Заголовок метаданих додає ~3 KB на всю активну дошку. Щотижневе архівування Done прибирає приблизно половину payload.

## 2. Що підказує сучасна практика PM / Kanban

### 2.1 Куди що класти (консенсус інструментів)

| Елемент | Практика | Джерело / сила |
|---|---|---|
| **Назва** | Коротка, дієслівна або з результатом, достатня, щоб впізнати роботу | GitHub Copilot best practices: «clear and descriptive title» [EXT]; studio-intake уже так робить [REPO]. **STRONG** |
| **Опис** | Контекст, мета й **критерії результату** («acceptance criteria»). Агентам потрібен саме результат, а не переказ брифу | GitHub Copilot coding agent docs [EXT]; дослідження «What Makes a GitHub Issue Ready for Copilot?» (arXiv 2512.21426) [EXT]. **STRONG** для агентів коду, **MEDIUM** для дизайну |
| **Статус** | Колонка/список = стадія потоку | Kanban [EXT]. **STRONG** |
| **Blocked** | **Прапорець на картці, що лишається у своїй колонці**, а не окрема колонка «Blocked»: інакше блоковані картки забувають і губиться стадія | ProKanban, Martin Hinshelwood (nkdagility), Mike Bowler [EXT, COMMUNITY-експертне]. **MEDIUM–STRONG** |
| **Пріоритет** | Малий фіксований набір + «без пріоритету». Linear свідомо не дає кастомних рівнів: «easy to get carried away with specificity» | [Linear Priority docs](https://linear.app/docs/priority) [EXT]. **STRONG** як патерн продукту |
| **Зусилля** | T-shirt sizing — відносна оцінка для швидкого планування. Мапінг у години «не точний і залежить від контексту»; одна команда має L, інша XL | Asana, KnowledgeHut, ActiveCollab [EXT]. **MEDIUM** |
| **Час на день** | Інструменти особистого планування (Sunsama) сумують **planned time** і показують попередження про перевантаження проти доступного часу | [Sunsama Planned & Actual](https://help.sunsama.com/docs/planned-and-actual-times) [EXT]. **STRONG** як патерн |
| **Когнітивне навантаження** | Deep/shallow як **мітка на розсуд людини**, не обов'язкове поле. Практика «енергетичних» тегів існує, але це персональна надбудова | Todoist Deep Work guide, практики Sunsama/Todoist [EXT, COMMUNITY]. **WEAK–MEDIUM** |
| **Наступна дія / waiting-for** | Кожен активний проєкт має наступну фізичну дію; окремий список очікувань переглядається щотижня | GTD Weekly Review [EXT]. **STRONG** як метод |
| **Чеклист** | Кроки всередині одного результату | Trello/Asana/Linear sub-issues [EXT]. **STRONG** |
| **Коментарі** | Хронологія, обговорення, рішення — append-only | Загальна практика [EXT]. **MEDIUM** |
| **Due** | Дата. **Важливість ≠ терміновість** (Eisenhower): терміновість похідна від часу | Класичний розподіл важливе/термінове [EXT]. **STRONG** як концепт |

### 2.2 Software / agile vs креативна фриланс-робота

- **Agile-команди** оцінюють, щоб планувати спринти й ділити роботу між людьми: story points, velocity, WIP-ліміти, типи задач, компоненти. Більша частина цього існує для **координації кількох людей**.
- **Соло-дизайнер із кількома клієнтами** має іншу проблему. Координації людей немає. Є **перемикання контексту між клієнтами, зовнішні очікування (фідбек, апрув) і нерівномірна глибина робіт** — від концепту до експорту.
- Висновок **[INF]**: із Jira-арсеналу для Daniel корисні лише:
  - статус через список;
  - прапорець «заблоковано»;
  - оцінка обсягу в годинах;
  - «наступний крок»;
  - «чекаю на».
  
  Типи задач, компоненти, story points, velocity, окремі поля ризику й складності — бюрократія без споживача.

## 3. Що підказує практика AI-agent + Kanban

### 3.1 Патерни з production-систем (не з демо)

| Система | Статус | Що робить | Урок для Djonik |
|---|---|---|---|
| **GitHub Copilot coding agent** | production | Issue — це специфікація: title, контекст, **measurable acceptance criteria**, розбиття великого на sub-issues | Поле «Результат» — найсильніший текстовий сигнал. Великі задачі розбивати |
| **Linear Agents + AIG** | production | Issue **делегують** агенту, але відповідальність лишається на людині («an agent cannot be held accountable»). Стан агента видимий | Djonik пропонує, Daniel підтверджує. Позначати, що саме записав агент |
| **Linear MCP** | production | Офіційний remote MCP, окремий `/readonly` endpoint, фільтри за priority/labels | Нативні структуровані поля + обмежена поверхня читання — еталон, до якого рухається Trello MCP |
| **Jira Rovo Delivery Agent** | production | Щоденний digest; «stale» визначає за часом **без руху**, а не за останньою активністю | Staleness — з історії (#36), не з `lastActivityAt` (у нас уже так) |
| **Microsoft Planner Agent** | production | Статус-звіти за період; людина редагує перед відправкою | Огляд — чернетка, не дія |
| **Anthropic: writing tools for agents** | офіційні настанови | Відповіді інструментів мають бути **компактні**; `response_format: concise/detailed`; розумні дефолти, пагінація, ~25k-токенна стеля | Малий фіксований заголовок у описі й менше Done-карток важливіші за багатство полів |
| **Anthropic: context engineering** | офіційні настанови | Just-in-time retrieval: легкі ідентифікатори, деталі — за потреби | Огляд дошки — компактно; деталі картки — прямим читанням |
| **Наш #31 / #36** | production-репо | Кожен запис має власну пост-перевірку; історія — з журналу Trello, не з моделі | Read-before-write, verify-after-write, append-only history — уже є |

### 3.2 Демо, не доказ

Community-огляди «Claude створив мені Trello-дошку» — це toy-сценарії ([Brittany Joiner, How To Trello](https://trello.substack.com/p/ive-been-talking-to-my-trello-boards) [COMMUNITY]; автор потім відмовилась від згенерованої дошки). Корисне спостереження: агент **адаптується до наявної структури без спецналаштувань**. Отже, щоб модель просто читала картки, окрема схема не потрібна. Схема потрібна, щоб модель **не вигадувала** відсутнє.

### 3.3 Відповіді на питання Audit 2

1. **Жорстко структурувати** (фіксований словник): статус (список), проєкт (label), due, `Обсяг`, `Зобов'язання` (так/ні + дата), `Чекаю` (так/ні), `Пріоритет`-виняток. Це факти, від яких залежать рішення і на яких модель вже помилялась.
2. **Лишити природною мовою:** результат, контекст, нотатки, наступний крок (одне речення), обмеження виконання.
3. **Можна виводити** (з позначкою «я б…»): порядок роботи, глибину фокусу, тип роботи, чи варто розбити задачу, як згрупувати день.
4. **Ніколи не виводити як факт:**
   - зобов'язання перед клієнтом;
   - відсутність ризику;
   - доступний час Daniel;
   - що Daniel працював над карткою;
   - час завершення;
   - розмір задачі **як записаний факт**.

   Частина цього вже в coordinator «Factual semantics» [REPO].
5. **Явним має бути:**
   - для планування — обсяг і стадія;
   - для навантаження — обсяг і доступні години (Memory-преференція);
   - для пріоритету — проєктний пріоритет (Memory) + винятки картки;
   - для ризику — зобов'язання і due;
   - для follow-up — «чекаю на» і дата перевірки (#34).
6. **Забагато схеми** — коли людина мусить вибирати значення, яке модель вгадала б так само добре, або коли більшість карток має дефолтне значення. Орієнтир: **≤ 3 рядки на типову активну картку**.
7. **Найвища віддача на одиницю зусиль:**
   1. `Зобов'язання` — рідко, але критично;
   2. `Обсяг` — одне слово;
   3. `Наступний крок` — одне речення;
   4. `Чекаю` — одне речення.

   Пріоритет і фокус дають мало, бо вже покриті Memory або виводяться. **MEDIUM**

## 4. Оцінка поточної архітектури Djonik/Trello

Стан дошки на 2026-09-23 [REPO, read-only замір §7.3]:
- одна дошка `Djonik`, списки `Inbox · Backlog · This week · In progress · Waiting · Done`;
- 41 відкрита картка: This week 11, In progress 2, Waiting 2, **Done 20**. Ще 6 відкритих карток лежать у списках, яких немає серед відкритих (ймовірно, архівних; варто перевірити);
- 5 project labels: Extract, Cossack Labs, Limen, A1, Seqthera; 6 карток без label;
- описи є у 15 з 41 карток, медіана 0 символів, максимум 1246, разом 6.6 тис. символів;
- Custom Fields: `Priority` (list: Highest / High / Medium / Low / Lowest / Not sure, на лицьовій стороні) і `Size` (list: S / M / L / XL / XXL, на лицьовій стороні). **Значення має лише 1 картка.**

Поточна семантика в інструкціях [REPO]:
- `task-management`: одна дошка, label = лише проєкт, нова задача → Inbox; label при create з перевіркою (#37); записи — create / update title / desc / due / move / done / label;
- coordinator «Factual semantics»: `lastActivityAt` ≠ робота; Waiting ≠ Blocked; `due` ≠ зобов'язання / capacity / ризик;
- daily / weekly: ранжують за due, стадією, waiting / blocked, явними пріоритетами, Memory; capacity — якісно; «Do not equate no due date with low urgency».

Оцінка за осями:

| Вісь | Стан | Оцінка |
|---|---|---|
| Проєкт | label, обов'язковий при create (#37) | Добре |
| Стадія | 6 списків | Добре; Backlog і Inbox варто розрізняти семантично (§10) |
| Важливість | Лише Memory (проєктний рівень) + розмова | Достатньо для проєктів, **немає винятків на картці** |
| Терміновість / зобов'язання | Лише `due`, свідомо не прирівнюється до зобов'язання | **Діра**: немає позитивного сигналу «це зобов'язання», тому модель вгадує в обидва боки (docs/39: «запас є»; docs/43: «без ризику») |
| Обсяг | Custom Field `Size`, невидимий для Djonik, фактично порожній | **Діра**: capacity не на чому рахувати |
| Фокус | Немає | Не критично |
| Наступний крок | Немає конвенції | **Діра** для In progress: план дня не знає, з чого почати |
| Waiting-for | Список Waiting без «на що / від кого» | **Діра** для follow-up (#34) |
| Blocked | Лише як поняття в інструкціях | Немає носія; для соло-роботи рідкісний стан (§10.10) |

## 5. Що ми вже робимо добре

1. **Одна дошка + project label + lifecycle lists.** Мінімальна структура, яку можна прочитати одним викликом `list_by_board`. Весь стек (#36 scope за label, #37 label при create, PH за label) узгоджений. **STRONG**
2. **Label означає лише проєкт.** Не змішувати семантики в labels — правильне рішення. Community-огляди прямо показують провал протилежного: «card labeled Blocked has been sitting there…» ([ContextBolt](https://contextbolt.com/blog/trello-mcp/) [COMMUNITY]).

## 6. Що слабке або переускладнене

1. **Custom Fields `Priority` і `Size` існують, але (а) невидимі агенту, (б) не заповнюються людиною.** Два незалежні сигнали, що поле не працює. Якщо паралельно вводити ті самі значення в опис, з'явиться подвійне введення і дрейф.
2. **Шестирівневий `Priority`** (Highest … Lowest + Not sure) для соло-роботи:
   - `Not sure` кодує «немає даних» як значення;
   - `Highest` / `Lowest` провокують інфляцію;
   - дубль того, що вже є на рівні проєкту в Memory.
3. **`Size` із XL і XXL**: для денного планування обидва означають «весь день або більше». Різниця «день» / «кілька днів» краще виражається явною оцінкою або розбиттям.
4. **Focus як третя обов'язкова вісь** — ціна на кожній картці заради сортування всередині дня, яке модель і так робить непогано.
5. **Немає носія для зобов'язання** — головний семантичний пробіл (§4).
6. **Done накопичується на дошці**: половина відкритих карток — Done. Це шум для планування, токени і ризик для детекторів #39.
7. **6 карток без label і 6 карток у невідкритих списках** — шум у кожному читанні дошки ([docs/25](25_PM_AGENT_BEHAVIOR_AUDIT.md) §4.4 уже фіксував шаблонні й тестові картки).
8. **Правила семантики вшиті в prompt і Skills, а даних, до яких вони застосовуються, немає.** Модель отримує «не вважай no-due низьким» без позитивного факту «ось зобов'язання». Заборони без даних дають вгадування в протилежний бік (docs/43 D). **Це центральний висновок аудиту.** **MEDIUM**

## 7. Можливості Trello MCP / API

### 7.1 Офіційний Trello MCP (`mcp.trello.com/v1`)

- Запущено 2026-07-22; OAuth 2.0; одна робоча область на з'єднання; видалення не підтримуються, лише архівування ([trello.com/mcp](https://trello.com/mcp), [ContextBolt](https://contextbolt.com/blog/trello-mcp/)) [EXT].
- За [README репозиторію](https://github.com/atlassian/trello-mcp-server) [EXT, STRONG] є інструменти для member, workspace, boards (view / create, view labels), lists, cards (view / create / update / move / archive / done, attach / detach labels), checklists, search, Planner, Inbox.
- **Roadmap («coming soon»):** Multi-workspace, **Activity & History**, **Comments**, **Attachments**, **«Custom Fields — View field definitions; get and set values on cards»**, створення labels, редагування дошки, копіювання карток, члени.
- **Терміну немає.** Atlassian у launch-треді казав, що «actively working on it» (за вторинним джерелом [ContextBolt](https://contextbolt.com/blog/trello-mcp/)). Developer changelog 2025–2026 не містить записів про MCP / Custom Fields ([changelog](https://developer.atlassian.com/cloud/trello/changelog/)) [EXT].
- Нюанс: вторинні огляди кажуть, що MCP «не читає коментарі». У нашому live-сліді `trelloReadCard get` повертає `comments []` ([docs/43](43_ISSUE_38_CONTRACT_DERIVED_LIVE_SMOKE.md) §5) [REPO]. Отже, поверхня вже могла змінитися. **Не спиратися на вторинні огляди — перевіряти probe.**
- Доступ до MCP «enabled by default for Enterprise and Premium» ([trello.com/mcp](https://trello.com/mcp)). Custom Fields доступні з плану Standard [EXT].

**Висновок:** обмеження тимчасове за намірами вендора, але без дати. Архітектура не має залежати від дати його зняття. **STRONG**

### 7.2 Trello REST

- Custom Fields повністю доступні:
  - `GET /boards/{id}/customFields` — визначення;
  - `GET /cards/{id}?customFieldItems=true` — значення;
  - **одним викликом** `GET /boards/{id}?cards=open&customFields=true&card_customFieldItems=true` ([Getting started with Custom Fields](https://developer.atlassian.com/cloud/trello/guides/rest-api/getting-started-with-custom-fields/)) [EXT, STRONG].
- Dropdown-значення приходять як `idValue`, тож їх треба розв'язувати через визначення поля. Це невелика нормалізація, але саме її мав би робити інструмент, а не модель.
- 2026-09-15: у Trello з'явилися OAuth 2.0 authorization code grants з гранулярними scopes і короткоживучими токенами ([changelog](https://developer.atlassian.com/cloud/trello/changelog/)) [EXT]. Для майбутнього власного read-only інструмента це безпечніша альтернатива довгоживучому API token.
- У репо вже є робочий read-only REST-патерн: `trello_work_history` (#36) з OAuth-заголовком, `TRELLO_READ_TOKEN`, custom tool в адаптері й ідемпотентним lifecycle #40 [REPO]. Метод `readCards` уже читає `/boards/{id}/cards/all`. Технічно `customFieldItems=true` — це один параметр.

### 7.3 Замір payload (read-only, 2026-09-23) [REPO]

| Запит (REST, 41 відкрита картка) | Байти |
|---|---|
| `cards/open` — усі поля за замовчуванням | 81 434 |
| те саме + `customFieldItems=true` | 82 701 (+1.6 %) |
| `cards/open?fields=id,name,idList,labels,due,dueComplete,desc` | 25 786 |
| **один виклик** board + cards (компактні поля) + CF-визначення + CF-значення + lists | 28 747 |
| `customFields` (визначення) | 2 103 |

Для порівняння: ваш MCP `list_by_board` ≈ 37 KB (зі слів probe). Отже, MCP уже частково урізає поля. Компактна власна проєкція була б на ~20–25 % меншою, але це не радикальний виграш.

### 7.4 Managed Agents MCP connector

- Приймає **лише remote MCP (`type: "url"`)**. Автентифікація — через vault (`static_bearer` або `mcp_oauth`) ([docs](https://platform.claude.com/docs/en/managed-agents/mcp-connector)) [EXT, STRONG]. Stdio-сервери (наприклад, `delorenj/mcp-server-trello`) напряму підключити не можна: їх треба хостити за URL з автентифікацією.
- **Вихід MCP-інструмента > 100 000 символів автоматично пишеться у файл пісочниці, а модель отримує обрізаний preview.** Зараз ~37 KB — це ~37 % порогу. Зростання дошки, довгі описи й накопичений Done зсувають нас до межі, де поведінка читання зміниться. **STRONG** щодо механізму, **MEDIUM** щодо часу настання.

| 23 | **Recurring / admin робота?** | **CHANGE**: не заводити картки на рутинну повторювану роботу; ритм (синки вт/чт) — у Memory. Разова адмін-задача з результатом — картка з label `Студія` | Інакше дошка забивається нескінченними повторами без результату | MEDIUM |

## 11. Рекомендована схема картки

### 11.1 Три кандидати на реальному прикладі

Картка: **Career Page UI**, label **Cossack Labs**, список **In progress**.

**MINIMAL**
```
Назва: Career Page UI — блок вакансій
Label: Cossack Labs · Список: In progress · Due: —
Опис:
Наступний крок: доробити блок вакансій і фільтр
```
- Daniel заповнює лише назву й наступний крок.
- Djonik не знає обсягу й зобов'язання, тому вгадує їх або постійно питає.
- Ціна мінімальна, але саме так і виникає помилка «без дедлайну → без ризику».

**BALANCED (рекомендовано)**
```
Назва: Career Page UI
Label: Cossack Labs · Список: In progress · Due: пт 26.09 18:00 (якщо є)
Опис:
Результат: сторінка Careers у Figma, desktop 1440, готова до передачі в розробку
Обсяг: M · ~2 год
Наступний крок: доробити блок вакансій і фільтр

---
mobile не потрібен. Референси — у вкладенні.
```
- Daniel пише 2–4 рядки й лише тоді, коли вони мають значення.
- Опційні рядки, лише коли є значення:
  - `Пріоритет: високий|низький` (виняток від проєкту);
  - `Чекаю: апрув від Анни`;
  - `Блокер: немає доступу до Figma-файлу клієнта`;
  - `Фокус: глибокий`.
- Нижче `---` — вільний текст людини.

**RICH (відхилено)**
```
[AI META]
Priority: Medium
Size: M
Focus: Medium
Type: UI
Risk: Low
Urgency: Medium
Dependencies: —
[/AI META]
Контекст: ...
Результат: ...
Наступний крок: ...
Зобов'язання: ...
Acceptance criteria: ...
```
- 8+ полів на кожній картці. Більшість значень дефолтні (`Medium`), тобто без інформації.
- `Risk` і `Urgency` — судження, які застаріють за день.
- Людина покине заповнення за тиждень. Це найімовірніший провал (§18, FM-1).

### 11.2 Вибір: BALANCED

Правила формату:
1. Заголовок **на самому початку** опису, по одному рядку на ключ, `Ключ: значення`.
2. Фіксований словник ключів: `Результат`, `Обсяг`, `Наступний крок`, `Зобов'язання`, `Чекаю`, `Блокер`, `Пріоритет`, `Фокус`. Інших ключів не вводити.
3. Фіксовані значення:
   - `Обсяг: S|M|L|XL` з опційним `· ~N год` або `· ~N дні`;
   - `Пріоритет: високий|низький`;
   - `Фокус: глибокий`.
   
   Решта ключів — одне коротке речення.
4. **Рядок присутній лише тоді, коли є значення.** Порожніх `—` не писати.
5. `---` відокремлює заголовок від вільного тексту людини. Роздільник рендериться Trello як лінія і легко розпізнається будь-яким парсером у майбутньому.
6. Ключі українською, бо це дошка Daniel. Моделі мова ключів не заважає: фіксованість важливіша за мову. **WEAK–MEDIUM**
7. Не довше ~5 рядків. Довгі брифи — вкладенням або посиланням, а не текстом в описі (токени, §16).

Хто що заповнює:

| Що | Daniel | Djonik (після підтвердження) | Automation | Djonik читає |
|---|---|---|---|---|
| Назва, проєкт | так (або через intake) | при create (#37) | — | так |
| Список | так | move (#31) | архівування Done (опційно, §15) | так |
| Due | так | set / change (#23) | — | так |
| Результат | коли неочевидно | з intake / розмови | — | так |
| Обсяг | так, одне слово | лише зі слів Daniel | — | так |
| Наступний крок | так | зі слів Daniel | — | так |
| Зобов'язання | так | лише зі слів Daniel | — | так |
| Чекаю / Блокер | так | зі слів Daniel | — | так |
| Пріоритет-виняток, Фокус | рідко | зі слів Daniel | — | так |

## 12. Модель прогресивного збагачення (Audit 4)

Гіпотеза з брифу (Inbox → This week → In progress з наростанням полів) **в основі правильна**. Прихована неконсистентність виникає лише тоді, коли модель трактує відсутнє поле як значення. Тому правило інтерпретації важливіше за правило заповнення.

| Стадія | Очікується | Якщо бракує |
|---|---|---|
| **Inbox** | назва (+ label, коли відомий) | нічого не просити; Inbox не планується |
| **Backlog** | назва, label | нічого не просити |
| **This week** | + `Обсяг`; `Результат`, якщо назва неоднозначна; `Зобов'язання`, якщо воно є | тижневий план показує «без оцінки: N карток» одним рядком і пропонує оцінити **пакетно** (понеділок) |
| **In progress** | + `Наступний крок` | денний план називає картку, але не вигадує крок; питає лише тоді, коли саме від цього залежить «з чого почати» |
| **Waiting** | + `Чекаю` (що / від кого) | п'ятничний огляд питає «на що саме чекаємо по X?» — один раз, не щодня |
| **Будь-яка** | `Зобов'язання`, `Блокер`, `Пріоритет` — коли з'являються | не питати про відсутність зобов'язання: відсутність — нормальний стан |

Що робить цю модель стійкою:
1. **Вимоги прив'язані до переходу, але не блокують його.** Trello не має валідації, і вона не потрібна.
2. **Збагачення — пакетне і в ритуалах** (понеділковий план, п'ятничний огляд #39), а не щоходу.
3. **Розмова як основне джерело.** Daniel каже «займе 2 години» → Djonik пропонує записати (§14). Руками в Trello заповнювати рідко.
4. **Ліміт нагадувань.** Про ту саму порожню картку — не частіше разу на тиждень; «не треба» поважається (узгоджено з принципами проактивності docs/25 §5.1).

Ціль по зусиллях Daniel: **0 секунд на Inbox; ~10–20 секунд на картку при плануванні тижня; ~5 секунд на оновлення наступного кроку.** **WEAK** (гіпотеза, перевіряється пілотом).

## 13. Поведінка Djonik за відсутніх або суперечливих даних (Audit 10)

Загальний принцип: **відсутнє — невідоме; невідоме, що змінює висновок, — назвати одним реченням; невідоме, що не змінює висновку, — мовчки обійти.** Питати лише тоді, коли відповідь змінить план, і не частіше разу на тему в ритуалі.

| Ситуація | Поведінка | Чого не робити |
|---|---|---|
| Немає `Пріоритет` | Застосувати проєктний пріоритет із Memory; якщо й там немає — рівний | Не писати «пріоритет середній» як факт |
| Немає `Обсяг` | Можна дати **власну грубу оцінку як судження** («я б заклав ~2 год, якщо це лише блок»); у сумі дня позначити «з оцінкою без підтвердження» | Не рахувати capacity так, ніби оцінка — факт; не записувати її в картку без підтвердження |
| Немає `Фокус` | Вивести з назви / результату як судження, лише якщо це змінює порядок | Не згадувати, що фокус «не вказано» |
| Порожній опис | Працювати з назвою, списком, label, due. Для In progress / This week, де назва неоднозначна, — одне питання в ритуалі | Не вигадувати результат чи контекст |
| Немає due | Нічого не виводити про терміновість із самої відсутності | **Не казати «без ризику», «не горить», «можна відкласти»** (docs/43 D) |
| Немає `Наступний крок` | Назвати картку в плані; якщо вона In progress і від кроку залежить старт — запитати або запропонувати крок **як ідею** | Не формулювати крок як записаний факт |
| Немає `Зобов'язання` | Мовчати про зобов'язання; ризик оцінювати лише з того, що є | Не казати «клієнт чекає» і не казати «клієнт не чекає» |
| **Конфлікт: CF каже M, опис каже 4–5 год** | Опис — джерело правди (§9). Сказати про розбіжність один раз, якщо вона впливає на план; порадити прибрати CF-значення | Не усереднювати, не вибирати мовчки |
| **Конфлікт: In progress, а наступний крок «чекаю апрув»** | Фактично це Waiting. Сказати одним реченням і **запропонувати** переміщення у Waiting (запис — лише після «так») | Не переміщати самому; не рахувати картку «в роботі» в навантаженні дня |
| Конфлікт: due у минулому, картка не Done | Назвати факт («due минув»); ризик — лише за наявності зобов'язання, інакше «варто перевірити, чи дата ще актуальна» | Не казати «прострочено перед клієнтом», якщо зобов'язання не зафіксоване |
| `Зобов'язання` є, due немає | Використати дату із зобов'язання як жорсткий орієнтир; порадити поставити due | Не ігнорувати зобов'язання лише тому, що в полі due порожньо |

Це розширення вже чинного coordinator-блоку «Factual semantics». Нові правила там не потрібні — потрібен короткий словник ключів (§21).

## 14. Чи має Djonik сам збагачувати картки (Audit 11)

Розрізняти три класи:

| Клас | Приклад | Політика |
|---|---|---|
| **Явний факт від Daniel** | «Career Page займе десь 2 години, там просто блок доробити» | **Можна записати після короткого підтвердження:** «Записати в Career Page: Обсяг M · ~2 год, Наступний крок: доробити блок?» → «так». Кілька карток — одне підтвердження. Після запису — verify за #31 |
| **Висновок моделі** | «це, схоже, концептуальна робота — глибокий фокус» | **Не записувати.** Лишається судженням у розмові з позначкою «я б…» |
| **Рекомендація моделі** | «я б розбив на дві картки» | Лише пропозиція. Виконання — окремий явний запит |

Чому не авто-запис явних фактів без підтвердження:
- product contract: записи — лише за явним запитом; автономні ходи Trello не змінюють ([docs/00](00_DJONIK_PRODUCT_CONTRACT.md));
- «займе 2 години» — це розповідь, не інструкція. Класифікація розповіді як мутації — саме той клас помилок, від якого захищає `task-management` («Advice is not mutation»);
- ціна підтвердження — одне слово, а ціна хибного запису — забруднене джерело правди.

**Пізніше (після пілоту):** якщо підтвердження виявиться шумом, Daniel може дати **стійкий дозвіл** (преференція в Memory) записувати явно названі ним обсяг і наступний крок без перепитування — з тією ж верифікацією і коротким звітом «записав». Висновки моделі все одно не записуються.

Технічні умови безпечного запису (**до реалізації, не зараз**):
1. `trelloWriteCard` оновлює `desc` **цілком**. Тому потрібно read → змінити лише рядки заголовка → зберегти решту байт-у-байт → write → verify. #31 уже порівнює `desc` точно [REPO], а ризик затерти текст Daniel закриває саме ця точна перевірка.
2. Вікно гонки з одночасним ручним редагуванням невелике, але реальне. Перед записом читати картку в тому ж ході, а не брати опис із попереднього.
3. Djonik ніколи не записує `Зобов'язання`, `Пріоритет` чи `Обсяг`, яких Daniel не казав.

Чи зменшить це ручну роботу? Так, суттєво: більшість метаданих народжується в розмові («це на завтра, там година роботи, чекаємо фідбек від Анни»). **MEDIUM** (патерн: Linear AIG — агент діє, людина відповідальна; Google CC / Gemini Brief — чернетки замість дій [docs/25](25_PM_AGENT_BEHAVIOR_AUDIT.md) §3).

## 15. Варіанти автоматизації / синхронізації (Audit 6)

### 15.1 Trello Automation (Butler) — чи може підтримувати `[AI META]` в описі?

| Питання | Відповідь | Джерело |
|---|---|---|
| Тригер на зміну Custom Field? | **Так**: «when custom field "Priority" is set» | [Custom Fields in automation](https://support.atlassian.com/trello/docs/working-with-custom-fields/) [STRONG] |
| Чи може читати значення полів? | **Так**: `{{%Field Name}}`, `{customfieldvalue}`, `{customfieldvaluebefore}` | [Automation variables](https://support.atlassian.com/trello/docs/automation-variables/) [STRONG] |
| Чи може змінити опис? | **Так**: «Set the card's description to …», з `{carddescription}` для поточного тексту | [Append text to description](https://support.atlassian.com/trello/docs/appending-text-to-a-card-name-or-description/) [STRONG] |
| Чи може **замінити** наявний блок? | **Ні.** Документація не має функцій replace / substring / regex. `{carddescription}` вставляє весь поточний опис. Wildcard `{*}` / `{matchedtext}` захоплює текст в умовах, але не вирізає його з опису | [Automation variables](https://support.atlassian.com/trello/docs/automation-variables/) [STRONG за відсутністю]; community-поради про «regex replace» стосуються застарілого Butler-бота, який більше не підтримується [COMMUNITY] |
| Повторні оновлення | Кожна зміна поля дописує **ще один** блок → дублікати ростуть | висновок із попереднього рядка |
| Збереження людського тексту | Лише якщо опис **повністю** належить автоматизації → людський текст ніде жити | висновок |
| Петлі | Правило «CF змінено → змінити опис» саме себе не тригерить, але поєднання правил може зациклитись (є community-кейси) | [Community: automation loops](https://community.atlassian.com/forums/Trello-questions/Prevent-looping-Trello-automation-when-using-several-tag/qaq-p/2645039) [COMMUNITY] |
| Квоти | Free 250 запусків / міс., Standard 1000, Premium / Enterprise без ліміту; до 20 дій на запуск | [Quotas and limits](https://support.atlassian.com/trello/docs/butler-quotas-and-limits/) [STRONG] |
| Production-придатність | **Ні** для синхронізації метаданих | — |

Обхідні шляхи й чому вони гірші:
- писати значення **коментарем** замість опису — коментарі не приходять у `list_by_board` і утворюють хронологію, а не поточний стан;
- тримати блок в **окремому** Custom Field типу text — MCP його так само не бачить.

Де Automation **корисна** без синхронізації метаданих (опційно, рішення Daniel):
- «щопонеділка архівувати картки в Done, що не змінювались 7 днів» — чистий win для токенів і шуму, історія лишається в журналі дій (#36);
- кнопка картки «→ Waiting», що дописує в кінець опису рядок `Чекаю: ` для заповнення. Дописування тут безпечне, бо разове.

### 15.2 Make / Zapier / n8n

- **Можуть** зробити правильну заміну блоку: webhook Trello → regex-replace в описі через REST.
- Але це нова зовнішня система з **write-токеном** до Trello, власною логікою, квотами й збоями. Це другий «записувач» опису поряд із Djonik і Daniel: гонки й дрейф, плюс новий шар безпеки. Протилежно принципу «Claude-native first, no custom infra without measured need» ([docs/01](01_CLAUDE_NATIVE_ARCHITECTURE.md) §12).
- Вердикт: **не рекомендується.** Джерело проблеми (дублювання) краще прибрати, ніж синхронізувати. **MEDIUM**

### 15.3 Power-Ups

Power-Ups (наприклад, Card Priority від Screenful) змінюють **відображення** і часто зберігають дані в pluginData / Custom Fields. Поверхню MCP вони не розширюють. Вердикт: **не допомагають агенту.** **MEDIUM**

## 16. Токени та виклики (Audit 8)

Відносне порівняння (за нашим заміром і ~37 KB MCP-payload):

| Підхід | Виклики на огляд дошки | Відносний обсяг | Латентність | Складність |
|---|---|---|---|---|
| `list_by_board` з описами (поточний) | 1 | 1.0× (~37 KB ≈ 9–10k токенів) | базова | базова |
| + заголовок метаданих в описах активних карток | 1 | ~1.08× (≈ +3 KB на ~20 активних карток по ~150 символів) | без змін | Skill-рядок |
| board + N `trelloReadCard get` | 1 + N | 2–4× залежно від N | ×N послідовних кроків моделі | погано |
| MCP + окремий CF-виклик (REST / custom tool) | 2 | ~1.1× | +1 крок | новий інструмент |
| Лише компактний custom snapshot з CF замість MCP | 1 | ~0.8× (≈ 29 KB) | базова | новий інструмент + друге джерело істини |
| **Архівування Done (20 з 41 карток)** | 1 | **~0.5–0.6×** | — | ручна дія / 1 правило Automation |

Висновки:
1. **Метадані в описі майже безкоштовні** за умови короткого заголовка. Вони приходять у тому самому виклику. **STRONG** (за заміром).
2. **Реальна загроза контексту — довгі вільні описи й Done-картки**, а не метадані. Максимальний опис уже 1246 символів. Кілька вставлених брифів — і дошка підходить до 100 000-символьного порогу, після якого Managed Agents кладе вихід у файл із preview (§7.4). Тоді модель може не побачити частину карток без додаткового кроку. **MEDIUM**
3. Позиція блоку: **на початку опису.** Якщо колись з'явиться обрізання тексту, то зазвичай обрізається хвіст, тож важливе має бути нагорі. Модель теж першим бачить головне. **WEAK–MEDIUM**
4. Нормалізація: фіксовані ключі й значення дешевші для міркування, ніж вільні фрази («десь пару годинок»). Модель однаково нормалізує, але кожного разу інакше. **MEDIUM**
5. Delimiter-блок `[AI META]` не потрібен, поки немає коду-парсера. `Ключ: значення` + `---` однаково легко парсяться в майбутньому (#39-детектори). **WEAK**

## 19. Рекомендована цільова архітектура (Audit 15)

| Елемент | Рекомендація |
|---|---|
| **BOARD** | Одна дошка `Djonik` |
| **LISTS** | `Inbox` (не розібране) · `Backlog` (прийняте, не цей тиждень) · `This week` · `In progress` · `Waiting` · `Done`. Без `Blocked`. Done архівується щотижня |
| **LABELS** | Лише проєкти / клієнти: Extract, Cossack Labs, Seqthera, A1, Limen + **`Студія`** для власної / адмін-роботи. Жодних семантик статусу, пріоритету чи типу |
| **TITLE** | Коротка назва роботи / результату, без назви клієнта, якщо вона не розрізняє картки |
| **DESCRIPTION** | Заголовок `Ключ: значення` (≤ ~5 рядків) → `---` → вільний текст. Довгі брифи — вкладенням або посиланням |
| **PRIORITY** | Не на кожній картці. Дефолт — проєктний пріоритет у Memory. На картці лише виняток `Пріоритет: високий` або `Пріоритет: низький` |
| **SIZE** | `Обсяг: S|M|L|XL` (S ≤ 1 год · M ~1–3 · L ~3–6 · XL ≥ день → розбити), опційно `· ~N год` / `· ~N дні`, що має пріоритет. Очікується з This week |
| **FOCUS** | Не поле. Опційний `Фокус: глибокий`, коли неочевидно; інакше модель виводить як судження |
| **DUE** | Записана дата. Не зобов'язання, не терміновість, не capacity. Відсутність нічого не означає |
| **CLIENT COMMITMENT** | `Зобов'язання: <кому / що / до коли>` — лише коли є. Головний сигнал ризику. Живий цикл перевірок — #34 |
| **BLOCKER** | `Блокер: <що заважає>` — рідко; картка лишається у своєму списку. Очікування на людину — це `Waiting` + `Чекаю:` |
| **NEXT STEP** | `Наступний крок: <одне речення>` — для In progress; бажано для This week |
| **CHECKLIST** | Підкроки одного результату (2–6), лише коли корисно (studio-intake). Дизайн-підстадії — тут, не в списках |
| **COMMENTS** | Хронологія, фідбек, рішення. Не джерело поточних метаданих |
| **CUSTOM FIELDS** | Не використовувати. Наявні `Priority` / `Size` приховати з лицьової сторони або видалити (рішення Daniel). Переглянути, коли офіційний MCP отримає CF read + write |
| **AUTOMATION** | Не для метаданих. Опційно: щотижневе архівування Done; кнопка «→ Waiting + `Чекаю:`» |
| **MEMORY** | Проєктні пріоритети й дефолти (вже є); калібрування Daniel («M для мене ≈ 2 год», «звичайний день ≈ N фокусних годин»); ритм (синки). **Жодних** станів карток, оцінок чи зобов'язань конкретних карток |
| **AGENT INFERENCE — дозволено (як судження, з «я б…»)** | порядок роботи; глибина фокусу; груба оцінка обсягу, коли його немає; пропозиція розбити; пропозиція перенести у Waiting; терміновість як висновок із явних фактів |
| **AGENT INFERENCE — заборонено (як факт)** | зобов'язання перед клієнтом; відсутність ризику; доступний час Daniel; пріоритет картки; що Daniel працював; коли завершено; обсяг як записаний факт; будь-що з відсутності поля |
