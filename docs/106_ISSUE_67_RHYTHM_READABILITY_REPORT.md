# 106 — Issue #67: читабельність повідомлень робочого ритму (source implementation report)

**Статус:** source-only, очікує review Product Owner. Без commit, push, deploy, змін `SERVING_RELEASE`, віддаленого Agent/Skills, Trello, Memory і без платної/live перевірки.
**Дата:** 2026-10-12. **Serving release у source:** r31 (не змінено). **База:** `main` після closeout #66.

## 1. Корінь проблеми

Причин дві, і вони в різних шарах.

**Слово `due` приходило з трьох місць, два з них — код.**

| Джерело | Де | Хто бачив |
|---|---|---|
| Підказки коду в prompt ритуалу | `src/rhythmSignals.ts`: `due 2026-10-05, ще не в роботі`, `due … минув`, `due … (наступний робочий день)` | модель, і вона повторювала слово («due на 05.10») |
| Приклад фрази в Skill | `planning-and-focus`: «вважаю, due внутрішній — якщо клієнт чекає, скажи» | модель; це пряма інструкція так говорити |
| Детальна хронологія work-history | `src/trelloWorkHistory.ts`: `…, due пт 27.03, 18:00` | Daniel напряму, через exact relay |

Skill `pm-rhythm` сам слова `due` у прикладах не мав, але й не забороняв його. Поле `due` у JSON `trello_board_snapshot` лишається: це назва поля для моделі, не текст для Daniel.

**Щільний вигляд задавав сам шаблон.** Понеділковий шаблон у `pm-rhythm` — це суцільні рядки без порожніх: `🎯 1. <результат> — <чому>`. Про групування за проєктами, жирний чи пункти Skill нічого не казав, а правило «no report headings» радше відмовляло від заголовків. Модель виконувала шаблон точно; коли проєктів кілька, виходив блок, де проєкт, задача й дата злиті в одне речення.

**Рендерер не був причиною.** Перевірено в source, не з пам'яті:

- Telegram отримує HTML (`parse_mode: "HTML"`), не Markdown і не MarkdownV2.
- `**жирний**` перетворюється на `<b>` у `renderTelegramHtml`; увесь інший текст екранується.
- Порожні рядки й «•» проходять без змін.
- Повідомлення ритму йдуть тим самим шляхом, що й звичайні відповіді: `createTelegramProactiveSender` → `sendFormattedMessage`.
- Якщо Telegram відхиляє розмітку, один fallback шле той самий текст без `parse_mode`: жирний тоді видно як `**…**`, але блоки й пункти лишаються.

Тобто жирний і порожні рядки вже працювали — модель просто не просили ними користуватись.

## 2. Що зроблено

**Код (діє після деплою застосунку, на чинному Agent v31):**

- `src/rhythmSignals.ts`: три підказки тепер кажуть `дедлайн <дата>` замість `due <дата>`. Ключі сигналів (`due-soon:…`, `kind:due_soon`) не чіпав: вони збережені в `/rhythm.md` і стані ритму як id для «не нагадуй».
- `src/trelloWorkHistory.ts`: у детальній хронології `, due пт 27.03` → `, дедлайн пт 27.03`. Це лише слово; числа, дедуплікація, шлюз `detailed` і relay з #66 не змінені. docs/104 §6 прямо відклав це слово на #67.

**Skill `pm-rhythm` (діє лише після нової версії Agent):**

- Два нові правила в «What every rhythm message is»:
  - **Plain words** — жодного `due`, ключів чи enum; дата картки як «дедлайн 05.10», «до 05.10» або «здати 05.10», одна форма на все повідомлення, лише дата з цього ходу.
  - **Easy to scan** — порожній рядок між блоками; один пункт лишається в рядку маркера, два й більше йдуть рядками «• », одна думка на рядок; кілька проєктів — окремі блоки з назвою жирним; тихий день, бриф з одним фокусом і виняток лишаються простими рядками. Порожні рядки в ліміт десяти не рахуються, пункти рахуються.
- Понеділковий шаблон: результати згруповано за проєктами. Ліміт той самий — три результати на весь план, не на проєкт. План в одному проєкті заголовка не потребує.
- Один робочий приклад із названими джерелами кожної дати (правило #45): 8 змістових рядків, тест тримає не більше 10.

**Skill `planning-and-focus`:** одне слово в прикладі фрази: «due внутрішній» → «дедлайн внутрішній».

Бриф вт–чт, п'ятничний ранок, п'ятничний огляд, тихий день і винятки структурно не змінені. Кнопки, callback-и, розклад, авторитет записів і Memory не чіпав.

## 3. Рішення щодо рендерера

Рендерер не змінював: він уже підтримує все потрібне, і це тепер доведено тестом на реальному шляху відправки. Ієрархія не залежить від жирного — блоки й пункти читаються й у plain-fallback.

Відхилені альтернативи:

| Альтернатива | Чому ні |
|---|---|
| Детермінований рушій верстки повідомлень | Немає доказів, що модель не тримає формат: її про нього досі не просили. |
| Заміна `due` → `дедлайн` у готовому тексті моделі на межі доставки | Латає симптом, ламає граматику («due-дата») і ховає справжні джерела слова. |
| Перейменувати поле `due` в snapshot | Це контракт інструмента для моделі; зміна зачепила б визначення й attestation. |
| Правило про слова в системному prompt | Змінило б `system` Agent і розширило б дельту r32; для ритму достатньо Skill. |

## 7. Обмеження й відкладене

- **Вигляд плану зміниться лише після нової версії Agent.** До неї production отримає тільки частину про слово: підказки коду й детальна хронологія. Модель на r31 і далі читатиме старі Skill-и, тож може сказати `due` сама, і план лишиться щільним.
- **Залежність релізу.** #70 зараз описує дельту r32 як «лише `work-review` + інструмент». Тепер у source є незасинхронізовані зміни ще двох Skill-ів: `pm-rhythm` і `planning-and-focus`. Потрібне рішення Product Owner: включити їх у r32 (розширити #70) чи випускати окремо. Це не блокує review #67.
- **Перевірка поведінки моделі відкладена.** У benchmark немає сценарію понеділкового плану; детермінований check «без `due`» і такий сценарій не додавав — це окремий платний крок за docs/04 §27.
- **Дата в підказці лишилась у форматі `2026-10-05`.** Перетворення на «05.10» робить модель; рік у підказці знімає двозначність.
- **Слово `due` в id для mute** (`[due-soon:…@…]`) лишається в prompt у квадратних дужках. Це непрозорий ідентифікатор; зміна зламала б збережені mute-и.
- **`task-management`** цитує репліку Daniel «забери due date» як вхідний запит. Це не мова Djonik, не чіпав.
- **Звичайні (не ритмічні) відповіді** отримали лише виправлений приклад у `planning-and-focus`. Загального правила про слова в системному prompt немає.
- **#69:** в огляді «Перейшло в Done: N» досі рахує події. Не чіпав.

## 8. Що перевірити вручну після нової версії Agent

1. Понеділковий план із кількома проєктами: блоки з жирною назвою, пункти, порожні рядки, жодного `due`, не довше ~10 рядків.
2. Понеділковий план в одному проєкті: без заголовка проєкту.
3. Бриф вт–чт і тихий день: прості рядки, як раніше.
4. П'ятничний огляд: блок фактів від коду без змін, текст моделі з ⏸.
5. «Покажи детально всі переміщення по CL»: у хронології «дедлайн», не `due`.
6. Кнопки «✅ Приймаю · ✏️ Змінити · 📋 Детальніше» працюють, як раніше.
