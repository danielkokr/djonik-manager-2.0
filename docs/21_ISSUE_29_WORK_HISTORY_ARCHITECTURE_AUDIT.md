## 1. Головний висновок

**[INF] #29 намагається відповісти на питання «що я зробив цього тижня?» без жодного джерела, яке містить відповідь. Потім він вимірює, наскільки гарно Haiku *відмовляє*.** Обидві платні діагностики (§29, §31) і невдалий production-attach (§26) використали саме такий prompt: «Що я реально зробив/завершив цього тижня по Extract?» На нього прийнятий контракт відповідає так: «не можу довести, ось поточний стан». Тож кожна ітерація тестувала формат відмови й дамп поточного стану, а не корисний продукт.

Проблема не в моделі, не в промпті і не у відсутності бази даних. **Потрібна історія вже існує, вона авторитетна, і її веде сам Trello.** Trello REST API віддає журнал дій дошки: `GET /1/boards/{id}/actions`, з `filter`, `since`/`before`, `limit` до 1000. У `updateCard` є `data.old` для `idList`/`closed`/`dueComplete`, тобто рух між списками, архівацію й позначку «виконано». Кожна дія має час і автора [EXT]. У Djonik немає лише **інструмента**, який це читає: офіційний Trello MCP досі тримає «View action history for cards, lists, and boards» у розділі «What's coming» [EXT]. Висновок discovery §17 «history-tool не існує в провайдера» правильний для MCP-сервера, але **не для Trello** [REPO → INF].

Так само роблять порівнянні продукти. Rovo Delivery Agent читає changelog Jira. ClickUp AI StandUp і Asana Smart summaries підсумовують активність за обраний період. Linear пише update про «changes made since the last update». Todoist MCP для «what did I complete?» викликає `find-activity` [EXT]. **Жоден із них не відновлює тижневу історію з агентної пам'яті й не заводить для цього власний event store. Усі читають історію, яку веде сама робоча система.**

**Рішення [INF]:**

1. **Закрити й замінити #29.** Його discovery, рубрик і невдалі прогони зберегти як історичні докази. Скасувати ціль «current-state review як відповідь на тижневе питання».
2. **Замінити на два bounded issue:** (a) нуль-вартісний spike, який перевіряє Trello action history для дошки Djonik; (b) один read-only детермінований custom tool `trello_work_history`. Він сам рахує вікно в Europe/Kyiv, переходи, покриття й формати дат, а модель лише коротко їх переказує.
3. **Власник: Haiku-координатор + детермінований інструмент.** Sonnet не потрібен. Помилки Haiku, які ми виміряли, — це обчислення, форматування й вибір даних, тобто саме те, що має робити код.
4. **Не будувати** event store, webhooks, snapshots чи окремий журнал для v1. Історія вже є в Trello. Епізодичний журнал розмов (Option D) відкласти до пілоту #35.
5. Якщо spike покаже, що історія Trello недоступна або непридатна, **work-review не входить у v1 взагалі.** Поточний стан уже покривають Project Health і task-management. Відмовний Skill не приєднувати.

## 4. Чому Trello + Claude Memory недостатньо (і чого насправді бракує)

### 4.1 П'ять різних видів «пам'яті» — хто їх зараз тримає

| Вид | Приклад | Хто тримає зараз | Надійність |
|---|---|---|---|
| **Семантична / стабільна** | «Extract = label на дошці Djonik; клієнт X; Daniel не працює у вихідні» | Claude Memory (project briefs, #12/#17) | Добра [REPO] |
| **Прийнятий план / зобов'язання** | «Цього тижня: Брендбук до пт, Флакони 7.5» | Claude Memory, вільний текст (#13) | Задовільна; без card ID, тому зіставлення з картками неоднозначне [REPO] |
| **Поточний операційний стан** | «Брендбук зараз у This week, due 25.09» | Trello через MCP (свіже читання) | Добра, з обмеженням #18 [REPO] |
| **Епізодична / спостереження** | «У вівторок Daniel сказав, що відправив бренд-бук на погодження» | Ніхто (лише транзієнтно в Session) | Відсутня |
| **Авторитетна історія подій** | «Картку перенесено This week → Done 19.09 о 14:02» | **Trello action log**, але Djonik його не читає | Дані існують [EXT]; інструмента немає [REPO] |

### 4.2 Чому цього не вистачає для «що я зробив цього тижня»

[INF] **Кожна з двох систем правильно тримає свій тип правди, але жодна з тих, що Djonik зараз читає, не тримає тип «подія в часі»:**

- Trello MCP віддає **знімок**. Поле `list` перезаписується; «зараз у Done» не каже «коли».
- Claude Memory — це **файли, які модель вирішила записати під час розмови**. Коли Daniel переносить картку в Trello UI, Djonik про це не дізнається: розмови немає, тож немає й запису. Memory має immutable versions (30-денне зберігання) [EXT], але це аудит змін *пам'яті*, а не роботи.
- Отже, щоб Memory стала журналом роботи, Djonik мав би **помічати кожну зміну в Trello**. Без webhooks чи опитування це неможливо, а дешевша альтернатива вже існує (§4.3).

### 4.3 Чи потрібна Djonik *власна* авторитетна історія?

[INF] **Ні.** Потрібен **доступ** до історії, яку вже веде Trello. Це відповідає правилу docs/03 §8: «Use the simplest reliable evidence source available rather than creating an event platform prematurely».

Чи вистачить дешевшого наближення (прийнятий план + поточний Trello + спостереження з розмов) для v1?

- **Для «чи виконано прийнятий план станом на зараз» — так.** Це вже прийнятий #29 plan-vs-current, за умови однозначного зіставлення карток.
- **Для «що я зробив цього тижня» — ні:**
  1. Значна частина руху карток відбувається в Trello UI поза розмовами, тож спостереження мали б дірки в покритті.
  2. Наближення змушує модель *виводити* хронологію, а саме це й було критичним режимом збою (§26).
  3. Корисна відповідь на тижневе питання — це факти про переходи з датами. Спостереження їх не дають.

**[INF] Висновок:** для v1 достатньо **план (Memory) + поточний стан (MCP) + журнал дій Trello (новий read-only інструмент)**. Епізодичний журнал розмов потрібен лише для роботи поза Trello (дзвінки, відправлені макети) і лише якщо пілот #35 покаже такі питання.

### 5.1 Відповіді на запитання §5 брифу по групах [EXT + INF]

- **Розрізнення чотирьох типів пам'яті.** PM-продукти (Jira, ClickUp, Asana, Linear, Todoist) його не потребують: вони самі є системою обліку, мають і поточний стан, і історію. Цілі/плани — окремі об'єкти (Linear updates, Sunsama objectives). Семантичну пам'ять про користувача зберігають мінімально. Агентні фреймворки (Letta, LangGraph, Zep, Managed Agents Memory) розрізняють semantic/episodic/procedural, але **не мають авторитетної історії зовнішньої системи**.
- **Модель чи детерміновані дані.** Скрізь дані й вікно часу детерміновані: date range, changelog, activity log, «since last update». Модель лише підсумовує. Todoist MCP переносить навіть вибір правильного запиту в інструкції інструмента.
- **Проактивний запис спостережень.** Linear нагадує лідам писати updates за розкладом; Sunsama веде ритуал. Агентні фреймворки пишуть пам'ять у hot path або у фоні (LangGraph). Жоден PM-продукт не будує історію роботи зі спостережень агента.
- **Вартість і складність.** Читати історію застосунку дешево (один API-виклик). Власна темпоральна пам'ять (Zep) чи event sourcing — це окрема інфраструктура, синхронізація й приватність.

## 6. Уроки зі схожих систем

1. **[EXT→INF] Історія живе в системі обліку.** Продукти відповідають на «що змінилось» з changelog чи activity log самого застосунку, а не з пам'яті агента.
2. **[EXT→INF] Вікно часу — параметр інструмента, а не модельна арифметика.** Asana вибирає дати, Todoist `dateFrom/dateTo`, Linear «since last update». У Djonik межу «цього тижня» у Києві має рахувати код.
3. **[EXT→INF] Інструмент віддає high-signal результат.** Anthropic радить повертати «only high signal information», прибирати низькорівневі поля, мати `response_format` concise/detailed і об'єднувати кілька викликів API в один інструмент. Вивід Trello MCP — повний вузол картки з `lastActivityAt`, ARI-id, `startedAt=null`, порожніми `members`. Це протилежність, і саме звідти частина збоїв.
4. **[EXT→INF] «Список завершених» ≠ «події завершення».** Todoist пише це прямо в інструкціях свого MCP. Djonik має розділяти «зараз у Done» і «перейшло в Done у вікні».
5. **[EXT→INF] Пам'ять агента — для рішень, контексту й відхилень, а не для журналу подій.** Letta, LangGraph і Managed Agents Memory підтримують рішення. Mem0 і Zep — механізми злиття чи інвалідації фактів із розмов, не системний журнал.
6. **[EXT→INF] Прийнятий план — це чекпоінт.** Linear будує update як діф від попереднього. Для Djonik прийнятий тижневий план (#13/#34) з card ID стає точкою відліку для plan-vs-actual.

## 8. Архітектурні варіанти

Колонки: **що розв'язує / що не може / складність імпл. / операційна / токени / приватність / режими збою / Claude-native? / v1? / вплив на #29**.

**A. Суворо current-state, без історії; покращити формат відповіді / модель**
- Розв'язує: «що зараз у Done». Не може: тижневе питання, тобто головну потребу.
- Імпл.: мала (вже є). Операційна: немає. Токени: 2–6¢ на Haiku.
- Режими збою: відмова на ключове питання; повторні промпт-ітерації.
- Claude-native: так. v1: **лише як fallback**, якщо Option E неможливий, і тоді без окремого Skill (PH + task-management уже покривають). #29: закрити.

**B. Перенести work-review до Sonnet (розширення PH)**
- Розв'язує: частину якості прози (стислість). Не може: відсутні дані; TZ-коректність (Sonnet лише уникнув конвертації, повернувши сирий ISO).
- Імпл.: середня (зміна прийнятого #28-шляху, relay, #32). Операційна: вища.
- Токени: ~4–5× Haiku (22–31¢ за хід [REPO]).
- Режими збою: вигадані сутності, багатослів'я (спостерігались у #28); бюджетні `budget_reached`.
- Claude-native: так. v1: **ні**. Сильніша модель над тими самими недостатніми даними — дорогий спосіб отримати гарнішу відмову.

**C. Гібрид plan-vs-current (Memory-план + поточний Trello, без хронології)**
- Розв'язує: «що з плану зараз зроблено». Не може: «що змінилось за тиждень», рух і reopen.
- Імпл.: мала. Операційна: немає. Токени: низькі.
- Режими збою: неоднозначне зіставлення назв; план без card ID.
- Claude-native: так. v1: **так, як частина рекомендованого**, з card ID від #34.

**D. Легкий епізодичний «робочий журнал» у Memory зі спостережень у розмовах**
- Розв'язує: роботу поза Trello (дзвінки, відправки, рішення). Не може: авторитетні переходи Trello; покриття поза розмовами.
- Імпл.: мала (Memory instructions + формат файлу `/journal/YYYY-Www.md`). Операційна: низька.
- Токени: +читання файлу тижня.
- Приватність: зберігає робочі епізоди в Anthropic Memory (уже прийнятий store).
- Режими збою: модель записує здогадки як факти; hot-path запис Haiku ненадійний; prompt injection у read_write store [EXT, попередження Memory docs].
- Claude-native: так. v1: **ні, відкласти до даних пілоту #35.**

**E. Нативна історія Trello (actions API) через bounded read-only інструмент** ← **рекомендовано**
- Розв'язує: рух між списками, Done, архівацію, `dueComplete`, створення, коментарі, актора, **з часом**, для вікна [EXT].
- Не може:
  - роботу поза Trello;
  - зміни label (`addLabelToCard`/`removeLabelFromCard` не повертаються у nested actions, лише webhook [EXT]). Проєкт визначаємо за *поточним* label, і про це треба сказати;
  - retention журналу дій **не перевірено** (перевіряє spike).
- Імпл.: мала–середня.
  - Custom tool у Managed Agent. Клієнт обробляє `agent.custom_tool_use` → викликає Trello REST → повертає компактний дайджест.
  - Треба розширити `connectToDjonik` обробкою `requires_action` для custom tool (зараз #32 трактує його як незавершений хід).
  - Або окремий read-only MCP-сервер (потребує хостингу).
- Операційна: новий секрет, read-only Trello token (як мінімум — перевірити scope у spike). Scheduled Deployments оминають `connectToDjonik` [REPO docs/01 §10], тож для майбутнього Wave D знадобиться MCP-варіант.
- Токени: **нижчі**, ніж зараз: дайджест із кількох переходів замість 31 повного вузла картки.
- Режими збою: пагінація/ліміт (1000/сторінку [EXT]); неповне покриття; розбіжність ідентичності дошки.
- Claude-native: так (custom tool — примітив №5 у CLAUDE.md). v1: **так, якщо spike PASS.** #29: замінює.
- Upstream: коли офіційний Trello MCP випустить «Activity & History» [EXT], custom tool замінити нативним.

**F. Webhook-шар спостережень (записувати зміни Trello в реальному часі)**
- Розв'язує: те саме, що E, плюс зміни label і реальний час для проактивності.
- Не може: нічого суттєвого понад E для v1.
- Імпл.: середня–висока: публічний HTTPS callback, HEAD-валідація, HMAC-SHA1 підпис, ретраї 30/60/120 с [EXT] і сховище.
- Операційна: висока (хостинг, пропущені події).
- Приватність: копія робочих даних у власному сховищі.
- Claude-native: ні (власна інфраструктура). v1: **ні.** Лише якщо E має недостатній retention, або для Wave D.

**G. Періодичні знімки / чекпоінти**
- Розв'язує: «що відрізняється між двома знімками». Не може: час і порядок переходів, проміжні рухи.
- Імпл.: середня (scheduler + сховище). Операційна: середня.
- Режими збою: відомий ризик із docs/16 §8 — діф знімків як «історія».
- v1: **ні.** Надлишково при E. Виняток — «чекпоінт» як **прийнятий план** (C), без окремого сховища.

**H. Власний append-only event store**
- Розв'язує: повну історію й темпоральні запити [EXT Fowler]. Не може: нічого понад авторитетний журнал Trello, який уже існує.
- Імпл./операційна: висока. Приватність: дублювання даних.
- Claude-native: ні (суперечить docs/00 §11). v1: **ні.**

**I. Краща архітектура, знайдена під час дослідження: «історія через інструмент + детермінований дайджест + тонкий наратив».**

Це E, розширене ідеями з Anthropic tool-writing guidance. Один read-only інструмент `trello_work_history(project_label, window="this_week"|"last_week"|{from,to})` детерміновано:
1. рахує межі вікна у Europe/Kyiv (пн 00:00 – зараз);
2. читає board actions з `since/before`, пагінує до вичерпання, фільтрує `updateCard` (`listBefore/listAfter`, `closed`, `dueComplete`), `createCard`, `commentCard` за поточним label проєкту;
3. віддає **лише high-signal**: назву картки, перехід, **локальний київський час і день тижня** (`чт 19.09, 14:02`), поточний список, `due` у Києві, лічильники за категоріями та флаги покриття (`pagesRead`, `truncated`, `labelHistoryUnavailable`). **Без** `lastActivityAt`, ARI-id і порожніх полів;
4. має `response_format: concise|detailed`, за замовчуванням concise: топ-N переходів + лічильники.

Модель (Haiku) пише 2–4 речення і, де доречно, одну наступну дію. Прийнятий план із Memory додається для plan-vs-actual за card ID. **v1: так (за умови spike).**

## 9. Рекомендована архітектура

### A. Корінна причина

**[INF] Djonik просять описати минуле, дивлячись лише на теперішнє. Історія роботи існує в журналі дій Trello, але Djonik не має інструмента, щоб її прочитати. Тому #29 витратив ітерації на те, щоб модель чемно відмовлялась і правильно рендерила сирі поля, які код мав би обчислювати сам.**

### B. Рекомендований продуктовий контракт

**Djonik обіцяє:**
- «Що змінилось у Trello за період» — переходи в Done/Waiting/In progress, архівація, повернення з Done, нові картки, коментарі. З київськими датами, за журналом дій Trello, для проєкту (поточний label) або всієї дошки.
- «Прийнятий план vs фактичні переходи» — коли план має card ID.
- «Що зараз у роботі» — через наявні PH і task-management.
- Явне покриття: «прочитано всю історію за тиждень» / «історія неповна: …».

**Djonik не обіцяє:**
- скільки часу чи зусиль Daniel витратив;
- роботу, якої не видно в Trello, доки немає журналу (Option D);
- продуктивність, скоринг чи «тиждень був продуктивним»;
- історичну аналітику трендів («що систематично зривається») — це після v1;
- приналежність картки до проєкту в минулому (зміни label не доступні через nested actions).

Формулювання для docs/00: розвести **«історичну аналітику» (після v1)** і **«тижневий огляд переходів із журналу Trello» (кандидат у v1)**. Це потребує рішення PO: поточний docs/00 відкладає «historical work analytics» цілком.

## 10. Рекомендований власник можливості

**Haiku-координатор + детермінований read-only інструмент `trello_work_history`. Не Sonnet і не розширення PH.**

Докази [REPO → INF]:

1. **Що Haiku зробив правильно в production-like контексті (§31):** знайшов дошку й label, п'ять свіжих читань, 0 мутацій, не використав `lastActivityAt`, не вигадав хронологію, дав чесне застереження. Виявлення й дисципліна меж працюють.
2. **Що Haiku зробив неправильно (§26, §31):** TZ-конвертація, лічильники, порядок з `lastActivityAt`, дамп, розмита фраза. Перші три — **обчислення**, які інструмент прибирає повністю: він віддає готові київські рядки, сам рахує і не віддає `lastActivityAt`. #23 уже показав, що правильне місце для TZ — код [REPO]. Дамп і розмита фраза — якість прози. Короткий дайджест (5 переходів замість 31 вузла) зменшує поверхню дампу.
3. **Sonnet не розв'язує корінь:** він працював би над тими самими недостатніми даними, коштує 22–31¢ за хід проти 6¢ [REPO] і в #28 теж вигадував сутність. Для щоденного PM-асистента з кількома review на тиждень різниця невелика в доларах, але велика в латентності та бюджетних ризиках (`budget_reached` у §26).
4. **Fallback:** якщо Haiku з дайджестом і далі порушує стислість чи додає непідтверджене у ≥2 з 5 семплів, наступним кроком є **детермінований шаблон «кістяка»** (інструмент повертає готові рядки-факти, модель додає одне речення). Сонет-власник — лише після цього і з виміряним обґрунтуванням.

## 15. Ризики та відкриті питання

1. **Retention журналу дій Trello не перевірено** (у знайдених джерелах про це нічого немає). Spike має це виміряти.
2. **Автентифікація.** Djonik зараз користується Trello через OAuth у vault MCP. Прямий REST потребує окремого токена в застосунку (новий секрет). Scope read-only і політика ротації — рішення PO.
3. **Custom tool і #32.** `requires_action` зараз трактується як незавершений хід. Потрібна акуратна обробка `agent.custom_tool_use` → `user.custom_tool_result` без поломки гарантій #32.
4. **Scheduled Deployments** оминають `connectToDjonik` [REPO]. Для майбутнього проактивного тижневого огляду знадобиться MCP-варіант або спільний tool-runner.
5. **Проєкт = поточний label.** Зміни label не видно в nested actions [EXT], тож картка, перенесена між проєктами, буде віднесена до поточного.
6. **Робота поза Trello** (Figma, дзвінки, пошта) лишається невидимою. Це свідоме обмеження v1, яке пілот має оцінити.
7. **Стислість Haiku** може лишитись проблемою навіть із дайджестом. План — fallback-шаблон (§10), а не Sonnet.
8. **Проміжні видимі повідомлення** в §31 («Змініть запит — це шукав карти, не дошки»). Якщо Telegram-клієнт віддає лише фінальне повідомлення (docs/16 §26.15), це не UX-проблема; інакше її треба окремо перевірити в #33.
9. **Потрібне рішення PO** щодо docs/00: v1 boundary зараз прямо відкладає «historical work analytics».
10. Ця рекомендація спирається на один production-like семпл Haiku (§31) і документацію Trello. Поведінку з дайджестом ще треба виміряти.
