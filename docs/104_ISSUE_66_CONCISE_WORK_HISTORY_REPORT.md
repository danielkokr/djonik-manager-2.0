## 1. Корінь проблеми

Три production-випадки (тижневий огляд, follow-up «тобто цей тиждень успішний?», «По CL, які задачі було закрито») мають одну причину з двох частин.

1. **Модель щоразу обирала `response_format: detailed`.** Це доводиться з коду, а не з припущення: мітки часу подій і значення `due` рендерить лише `buildDetailedAnswerText` → `renderCategoryFactLines`. Стислий Variant B їх не містить узагалі, тож блок із «Done/Created/move + час + due» міг бути тільки `detailed`. Production-трейс я не читав (він на хості), тому сам факт вибору моделі — висновок із форми виводу, а не зі спостереженого виклику.
2. **Це був раціональний вибір, а не випадковий дрейф.** `concise` називав щонайбільше 5 карток у Done («(ще 6)»), а створені й переміщені показував лише числом. Єдиним способом дізнатися всі назви був `detailed`. А exact relay (#36) показує `answer_text` Daniel дослівно й безумовно — тож усе, що модель брала як матеріал для висновку, ставало видимим дампом. Інструмент зчепив «що потрібно моделі» з «що бачить Daniel».

Що перевірено й відкинуто:

| Гіпотеза | Результат |
|---|---|
| Friday/Working Rhythm примусово просить `detailed` | Ні. `buildRitualPrompt` і `pm-rhythm` формат не згадують. |
| Scheduled та interactive йдуть різними шляхами | Ні. Обидва — один `trello_work_history` → один relay у `djonikClient.ts`. |
| Застарілий Skill на сервінгу | Ні. r31 пінить `work-review` з рядком «Choose `concise` unless Daniel asks for detail». Інструкція була, але не трималась. |
| Тести закріплюють стару багатослівність | Частково: один тест закріплював ліміт 5 назв саме для проєкту. |
| Дефект нижче продуктового шару | Ні. Lifecycle #40 і relay #36 працюють як задумано. |

## 2. Що зроблено

**Код (діє одразу після деплою застосунку, на чинному Agent v31):**

- `detailed` більше не вирішується самим вибором моделі. Клієнт визначає факт «Daniel у власному повідомленні цього ходу прямо попросив деталі» і передає його виконавцю. Без цього факту `detailed` повертає звичайну стислу відповідь плюс `detail_note` — пояснення лише для моделі, Daniel його не бачить.
- В автоматичному ході ритму цей факт завжди `false`, тож п'ятничний огляд не може видати хронологію.
- Огляд по проєкту називає закриті картки (до 15), а не обрізає на п'яти. Огляд по дошці лишився з п'ятьма назвами.
- Дозвіл діє на один хід: наступне звичайне питання знову стисле.

**Новий явний намір `focus`** (`overview` | `completed` | `returned` | `created` | `archived` | `moved`). Вузьке питання отримує рівно свій зріз:

```
Cossack Labs — закрито цього тижня:
• Whitepaper PDF
• Футболка
• RDAS
…
11 унікальних карток. Одна картка заходила в Done двічі.
```

Без інших категорій, часу, `due` і хронології. Виконавець уже приймає `focus`, але **модель зможе його передати лише після наступної версії Agent** (див. §7).

**Skill `work-review`:** рядок «Choose `concise`…» замінено абзацом: один виклик, `focus` під питання, `detailed` лише на прямий запит, follow-up без повторного виклику.

**Governance:** у `docs/02` додано мінімальний update — #66 є bounded NOW з пілота #35; #35 триває паралельно.

## 3. Чому така архітектура

- **Факти лишаються детермінованими.** Нових структур для вільного переказу модель не отримує; усі числа, дедуплікація й попередження про покриття рахує код.
- **Шлюз за фактом ходу, а не за параметром моделі.** Параметр уже дрейфував у production попри інструкцію в Skill. Правило «детальна хронологія лише після явного запиту» — це acceptance criterion, тому його тримає код.
- **Шлюз лише дозволяє.** Модель теж має попросити `detailed`. Хибний збіг слова сам нічого не показує; промах коштує однієї стислої відповіді й рядка про те, як попросити деталі.

Відхилені альтернативи:

| Альтернатива | Чому ні |
|---|---|
| Лише посилити Skill/опис інструмента | Така інструкція вже була і не втрималась. Нічого не дає до віддаленої синхронізації. |
| Дати моделі сирі факти окремим полем, показувати стисле | Повертає клас помилок docs/27–29 (модель переписує числа). Прямо заборонено постановкою. |
| Змінити чинне визначення інструмента | Attestation порівнює Agent із source-визначенням, тож ревізія перестала б стартувати на r31. |
| Не показувати повторно той самий блок у follow-up | Додатковий стан у клієнті й ризик сховати огляд, який Daniel просить удруге. |

## 6. Свідомо відкладено

- **#67:** слово `due` у детальній хронології, булети/жирний у Variant B, ієрархія Working Rhythm. Формат огляду не чіпав.
- **#69:** в огляді «Перейшло в Done: N» досі рахує події, а не унікальні картки; оцінка «чи успішний тиждень» не вирішена. **Пряма залежність:** зріз `completed` мусив показати унікальну кількість, бо це і є очікувана відповідь із #66. Тому до #69 огляд і зріз можуть показати різні числа для одного тижня (у прикладі 12 подій проти 11 карток).
- **Follow-up на r31:** якщо модель знову викличе інструмент, Daniel побачить стислий блок удруге. Дампу не буде, але повтор лишиться до синхронізації Skill.
- **Контекстна згода:** «так, покажи» після пропозиції Джоніка не відкриє хронологію — потрібне слово на кшталт «детально». Список фраз короткий і живе в `DETAIL_REQUEST`.
- `RELEASE_R32_CANDIDATE` не оголошував: чинний механізм кандидатів не вміє виразити зміну визначення вже наявного інструмента (§7).

## 7. Віддалена синхронізація

Потрібна пізніше, окремим авторизованим issue (як #64/#65):

1. Нова версія Skill `work-review` з поточного source.
2. Нова версія Agent, де `trello_work_history` має визначення `TRELLO_WORK_HISTORY_TOOL_NEXT`.
3. **Обидва разом, в одній версії Agent.** Skill без нового інструмента змусить модель передавати `focus`, якого чинна схема (`additionalProperties: false`) не приймає.
4. Перед цим release-інфраструктурі потрібна підтримка визначення інструмента на рівні релізу: `SUPPORTED_CUSTOM_TOOLS` зараз одне на всі релізи, а r31 має лишатись attestable як rollback.

До того часу деплой самого застосунку вже прибирає дамп у всіх трьох випадках; точний зріз за `focus` з'явиться після кроків 1–3.

## 8. Що перевірити вручну після деплою

На r31 (лише деплой застосунку):

1. П'ятничний огляд або «дай огляд тижня» → короткий блок без часу подій і `due`, далі PM-висновок.
2. Одразу після: «тобто цей тиждень успішний?» → без хронології.
3. «По CL, які задачі було закрито» → огляд по Cossack Labs з усіма назвами закритих карток, без хронології.
4. «Покажи детально всі переміщення по CL» → повна хронологія.
5. Після п.4 звичайне питання про тиждень → знову стисло.
6. Проєкт із понад 15 закритими картками → назв 15 і «(ще N)».

Після синхронізації Agent/Skill додатково: п.3 має дати рівно список «• назва» з рядком про унікальні картки; «що створили цього тижня по Extract?» → лише створені.
